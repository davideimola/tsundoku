# Drizzle owns the migrations, and the schema is still SQL

Migrations are generated by **drizzle-kit** from `db/schema.ts` and applied by Drizzle's
migrator. The hand-written runner in `db/migrate.ts` and its `<issue>_<step>` naming are
gone.

`src/core` connects through Drizzle too, and the typed schema is available to it. **The
queries are not converted, and the line is drawn on purpose**, so it is worth stating where.

A query that derives nothing — two columns off a vocabulary table in a stated order — is
written against the schema and typed from it. `listBindings`, `listTypes` and
`listProvenances` are that, and they read better for it.

Everything else stays SQL. These queries are not CRUD: `join lateral … on true` so a Story
nothing carries yields no row rather than a row to check for; `unnest($1::uuid[])` to ask
about many at once; `jsonb_build_object` to shape an answer; and fragments — `IN_THE_HOUSE`,
`CARRIER`, `BEST_CARRIER` — composed into several queries so one rule is written once.
Ten CTEs and five lateral joins across `src/core`. A builder expresses the simple half of
that and says the rest through `sql` templates anyway, which is the same SQL with more
ceremony and one more way to write it. `src/core/db.ts` keeps that reasoning where a reader
of the queries will meet it.

## What forced it

The old convention numbered a migration by the GitHub issue that added it, and the runner
refused a file that sorted before one already applied — correctly, because applying it
would give that database an order no fresh clone reproduces. Two migrations were named
`0020_*` for an issue that does not exist. From then on **every number the convention would
actually produce sorted behind them and was refused.** Adding one row to the `binding`
table hit this twice: once on the cluster's database, once on the local one.

Drizzle numbers sequentially from a journal it owns. The whole class of problem goes.

## What was measured before deciding

`drizzle-kit pull` was tried first, to generate `0000` from the live database. **It is lossy
against this schema**, and the losses are not all cosmetic:

| | |
|---|---|
| operator classes | assigned to the wrong columns — `story_id` (uuid) got `date_ops`. The generated file did not run at all. |
| composite index column order | scrambled: `(story_id, person_id, role_id)` came back as `(person_id, role_id, story_id)` |
| `desc`, `nulls last` | dropped |
| **`nulls not distinct`** | **dropped — on two unique indexes, where it is the invariant** |
| the trigger function and its two triggers | not modelled |
| all 56 `comment on` | not modelled |

The fourth row is the one that matters. Without `nulls not distinct`,
`rating_is_one_per_story_and_reading` stops holding: two ratings with a null `reading_id`
on one Story become legal, and nothing fails until a duplicate appears.

So `0000` is **not generated**. It is `pg_dump --schema-only` of the database the seventeen
hand-written migrations produced, verified object-for-object against it — columns, indexes,
checks, foreign keys, the function, the triggers and every comment. `db/schema.ts` was then
corrected by hand until the SQL *it* generates produces that same schema, so the diffs
Drizzle writes from here are taken against a description that is true.

## What this costs, stated rather than discovered later

**Generated migrations carry no `comment on`.** This schema has 56 of them and they are
where it documents itself. Every generated migration that adds a table or a column needs
them appended by hand, or the practice dies quietly and the schema stops explaining itself.

**Postgres past the DSL stays hand-written for ever.** `volume_holds_one_position()` and its
two triggers are SQL in `0000` and will be SQL in any migration that changes them. Drizzle
does not model PL/pgSQL and is not going to.

**The vocabularies are rows, so Drizzle will never write them** (ADR-0006). They are their
own migration, `0001`, and each new one after it is another hand-written file.

**A seed assembled from old migrations is not the state they produced.** Writing `0001` by
copying their `insert`s brought back `converted-from-a-coarser-scale`, a Provenance ADR-0008
had deleted on purpose. `rating.test.ts` caught it. Replaying inserts is not the same as
dumping the result of replaying them.

## Considered and not taken

- **Keep the hand-written runner, renumber sequentially.** One line of convention and half
  an hour, and it fixes the only problem that actually blocked anything. Rejected by the
  owner in favour of the generator, which also removes the class of mistake rather than the
  instance.
- **`drizzle-kit pull` as the baseline.** Rejected on the evidence above.
- **Drizzle's `migrationsTable` pointed at `schema_migrations`.** The old ledger's columns
  are `filename, checksum, applied_at`; Drizzle's are its own. Two ledgers under one name is
  worse than one ledger under a new name, so the old table is dropped and Drizzle keeps
  `drizzle.__drizzle_migrations`.
